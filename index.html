Deepest technical build
Featured: Job Application Tracker — Ingestion, Matching & Analytics

This is the project I'd walk an interviewer through first — it's the one where the backend does real decision-making, not just CRUD.

Why this one

The original app was a straightforward MERN-style CRUD tracker. I extended it into a full pipeline: jobs now arrive through manual entry, Gmail inbox scanning, a Manifest V3 browser extension, or a live discovery API, get deduplicated and scored against a stored profile, and feed a per-user analytics dashboard — all sharing the same PostgreSQL database (via Prisma) and Express app as the original tracker.

Architecture

API process (Express 5) stays thin and fast. Worker process (npm run worker) runs five separate BullMQ workers — ingest, match, apply, analytics, and scrape — as their own Node process, so a Playwright crash can never take the REST API down. Data access is Prisma-first, with a thin $queryRawUnsafe wrapper for the SQL-heavy analytics and dedup queries. Redis backs the queues and a per-domain token-bucket rate limiter with randomized human-like delays.

Matching logic

Two scorers: a free-tier TF-IDF + keyword matcher (scoreTfIdf) that needs no external API, and an embeddings-based scorer (scoreEmbedding) that takes an injected embedFn so it isn't locked to one provider. A learning service nudges per-skill weights up or down based on real interview/offer/rejection outcomes.

Deduplication

Incoming listings are deduplicated with exact hashing first, then fuzzy matching — Jaro-Winkler similarity on the title plus TF-IDF similarity on the description — before they're inserted and enqueued for scoring.

Data model

A single hosted PostgreSQL instance, accessed through Prisma, backs both systems: jobs, companies, applications, match_scores, user_profile, job_sources, analytics_daily, and scrape_runs, alongside the original tracker's users/tracked_jobs tables — one schema, no data duplication between the two systems.

What I'd improve next

LinkedIn/Indeed discovery is intentionally stubbed as "unavailable" — neither offers a public, credential-free search API, and the project deliberately avoids scraping or anti-bot bypasses to fake it. Real next steps called out in the repo: add a stage-history table so analytics can measure "ever reached Interview/Offer" instead of only current status, and move matching to pgvector-backed embeddings once the corpus outgrows TF-IDF.

        Under the hood
        Engineering Depth

        The backend decisions behind the three projects above — APIs, data modeling, and systems, not just UI.

        🔌 APIs

        • 30+ REST endpoints across auth, resource CRUD, search, comparison, recommendation, and analytics
        • Zod-validated request bodies on College Discovery's route handlers
        • Consistent auth pattern: JWT in HTTP-only cookies (College Discovery) vs. bearer-style token header (Forum, Tracker)
        • Server-side AI proxy route (Groq) so API keys never reach the client

        🗄️ Database Design

        • Relational schema (PostgreSQL + Prisma) with indexed lookup fields, cascade-safe deletes on Course/Review, and a unique (userId, collegeId) constraint on saved colleges
        • NoSQL schema (MongoDB + Mongoose) for the forum's Users/Posts/Comments/Notifications with reference-based relations
        • Single shared Postgres instance in the Job Tracker, accessed through Prisma, serving both the CRUD tracker and the matching engine's 8-table schema

        🏗️ System Architecture

        • API and background-worker processes fully decoupled (BullMQ + Redis) so a scraper crash can't take down the REST API
        • WebSocket layer (Socket.IO) running alongside a REST API for hybrid real-time + persistent state
        • Middleware-centralized access control (Next.js middleware checks the JWT cookie before requests reach route handlers)

        ⚡ Performance & Reliability

        • Redis token-bucket rate limiting per target domain plus randomized delays to avoid hammering third-party sites
        • Exact-hash + fuzzy (Jaro-Winkler / TF-IDF) deduplication to avoid reprocessing duplicate listings
        • Global Prisma Client reuse in development to prevent connection churn on hot reload
        • Single-use, expiring password-reset tokens instead of long-lived links
